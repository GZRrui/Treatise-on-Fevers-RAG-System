# 企业级改造路线：阶段0至阶段7

## 1. 状态声明

撤回“阶段一已签收”的结论。

当前工作区包含模块化单体、证据策略、原子索引、管理安全和评测脚本等不同成熟度的成果，但这些成果尚未按照“单阶段、单目标、可独立交付、可独立回滚”的方式拆分。因此当前状态定义为：

> 高阶集成原型已通过技术验证；阶段0已按 Windows 目标环境签收，阶段1进入实施但尚未签收。

已有成果不直接删除。应先建立可追溯快照，再按依赖关系拆成独立提交和特性分支，分别进入对应阶段验收。

## 2. 专家建议采纳与修正

采纳：

- 增加阶段0，先锁定依赖、环境、数据和原始系统基线。
- 阶段1只处理模块化单体和原主链路缺陷，不混入检索策略与索引生命周期扩展。
- 当前高阶成果必须隔离后逐项合并。
- 在任何索引质量结论前补全数据完整性和来源报告。
- 增加阶段1.5检索质量专项，先达标再迁移 pgvector。

修正：

- 阶段1.5依赖 Recall/MRR，因此阶段0必须有最小可复现评测快照；阶段4是评测平台化和持续回归，而不是第一次引入评测。
- 管理安全不能在存在管理 HTTP 接口时撤掉。阶段1推荐关闭索引构建 HTTP 接口，仅保留受控 CLI；阶段2恢复异步管理接口时合并管理安全能力。
- 当前所有改造尚未形成独立提交，不能直接使用 Git 回退或简单搬分支。必须先快照，再按文件和行为依赖拆分。

## 5. 全阶段共同工程原则

### 5.1 分层与依赖

- Domain 只包含稳定业务概念，不导入 FastAPI、SQLAlchemy、LlamaIndex 或 Worker SDK。
- Application 只编排用例并依赖窄端口，不读取全局配置，不使用 Service Locator。
- Infrastructure 实现文件、模型、数据库、队列和第三方适配。
- API 只完成鉴权、校验、DTO映射和协议处理，不写业务规则。
- 所有运行依赖只在 API/Worker 各自组合根创建。

### 5.2 SOLID

- SRP：一个模块只拥有一个变化原因。
- OCP：新增存储、检索策略和 Worker Adapter 不修改核心用例。
- LSP：所有 Adapter 必须通过同一端口契约测试。
- ISP：按调用者拆分窄端口，禁止万能 Repository、万能 Service。
- DIP：内层定义端口，外层实现；禁止 Domain/Application 反向依赖框架。

### 5.3 坏味道禁止项

- 禁止全局可变引擎、隐式单例和跨请求共享可变集合。
- 禁止组件内部 `from config import settings`。
- 禁止路由直接调用 LlamaIndex、SQL 或文件系统。
- 禁止 `except Exception: pass`、伪成功响应和吞异常。
- 禁止使用布尔参数持续扩展行为；超过两种策略时使用明确命令或策略对象。
- 禁止以 `Any` 贯穿核心层；第三方动态类型必须在 Adapter 边界收窄。
- 禁止重复 DTO、重复鉴权、重复配置解析和散落字符串状态。
- 禁止无业务含义的 `utils.py`、循环依赖和跨层反向导入。
- 单函数保持单一抽象层；复杂度超标时先拆职责，不以注释掩盖结构问题。

### 5.4 每阶段强制门禁

- `compileall`、Pytest、Mypy strict、Ruff、前端 typecheck/build。
- 架构依赖测试和 Adapter 契约测试。
- 变更必须附 ADR或设计说明、测试证据、迁移步骤和回滚步骤。
- 单元测试不得访问真实网络、真实 `storage` 或真实 `data`。
- 依赖、OpenAPI、数据 schema 和迁移文件均纳入版本控制。
- 已知缺陷不得通过降低阈值、扩大异常捕获或隐藏状态解决。

### 6.2 输入、输出与非目标

**输入**

- 原始提交 `37d2c122cee1956c83d99f64996b4f15976053d4`、当前 `data/` 数据文件、依赖声明和前端 lockfile。

- 缺陷台账、ADR、CI 门禁和明确的阶段1输入清单。

## 7. 阶段1：模块化单体

### 7.1 目标

在阶段0证据可复现的前提下，只调整结构、依赖方向和台账中批准的主链路缺陷；除这些缺陷修复外保持行为兼容。阶段1的完成标志是可审查的模块化单体和稳定 HTTP 契约，不是检索质量提升。

### 7.2 输入、输出与非目标

**输入**

- 阶段0锁文件、环境矩阵、原始 OpenAPI/样例/质量快照和缺陷台账。
- 仅限 `API-001`、`API-002`、`INDEX-001` 及其依赖的分层改造；每项变更必须有回归测试。

**输出**

- `domain/application/infrastructure/api` 四层边界、唯一组合根和窄端口。
- `top_k`、SSE delta、错误 envelope、liveness/readiness、空索引启动的实现与回归证据。
- 阶段1 OpenAPI 差异报告、兼容性报告、迁移/回滚说明和 `docs/phase-1-acceptance.md`。

**非目标**

- 不合并证据三级策略、generation/CAS/文件锁、Worker、队列、pgvector 或动态 Registry。
- 不改变检索算法、阈值、Prompt、数据分母和索引格式。
- 不把索引构建作为公共业务 HTTP 能力；阶段1只允许受控 CLI 离线构建，状态接口保持只读。

### 7.3 工作包

- 建立 `domain/application/infrastructure/api` 边界和唯一组合根。
- 消除全局引擎、全局配置读取和启动时隐式构建。
- 修复 `top_k` 从 HTTP 到 Retriever 的完整传递。
- 修复累计流式内容到增量 delta 的转换、断开处理和资源释放。
- 统一错误码、HTTP状态和响应 envelope。
- liveness 与 readiness 分离。
- 多古籍只预留 `KnowledgeBaseKey`、Catalog 和路径隔离，不穿透 QA/Search。
- 阶段1不暴露索引构建 HTTP 接口；使用 CLI 离线构建已批准的基线索引。

### 7.4 明确排除

- 不合并证据三级策略。
- 不合并 generation/CAS/文件锁。
- 不引入 Worker、数据库队列、pgvector。
- 不改变检索算法、阈值和 Prompt。
- 不新增动态 Registry。

### 7.5 验收

- **结构**：架构测试证明 Domain/Application 不导入 FastAPI、LlamaIndex、SQLAlchemy、`src` 或文件系统；运行依赖只从组合根显式注入。
- **top_k**：QA、Search 的 HTTP `top_k` 在边界校验后原值传到 Retriever，响应结果数不超过请求值；有端到端回归证据。
- **SSE**：每个内容事件只携带自上一个事件以来的 delta；来源、内容、结束、错误事件顺序和客户端断开时的资源释放均有测试；正常流恰好一个结束事件，错误流不得伪造成功。
- **错误契约**：验证错误、未就绪、冲突和未处理异常分别映射到批准的 HTTP 状态、稳定错误码和统一 envelope；不得泄露密钥或堆栈。
- **索引启动**：空索引不会在 API 进程内同步重建；服务以明确的 not-ready 状态启动，构建仅通过受控 CLI，并保留旧可用索引行为。
- **健康检查**：`/health` 只表示进程存活，`/health/ready` 反映依赖和索引可用性，二者状态码和响应字段有契约测试。
- **兼容性**：除批准修复和移除公共索引构建路由外，OpenAPI、请求/响应字段和同一输入的检索/问答结果在允许误差内保持一致；质量、P50/P95 和错误率相对阶段0不得无解释退化。
- **证据与回滚**：每项门禁都有测试输出、OpenAPI diff、架构报告和回滚步骤；阶段1未满足任一项不得签收或进入阶段1.5。

## 8. 阶段1.5：检索质量专项

### 8.1 前置条件

- 权威数据分母和清洗规则已经确认。
- 索引覆盖率达到100%，或每个排除项有书面原因。
- 阶段1行为与架构已签收。

### 8.2 工作包

- 先做漏召回分层诊断：数据缺失、切分、Query变体、向量模型和排序问题分开统计。
- 建立 exact、paraphrase、方剂、症状、篇章、hard-negative 等数据切片。
- 将 dense、lexical、hybrid、Reranker 实现为独立 Retrieval Adapter/Strategy。
- 使用成熟检索和排序库，不手写BM25、分词器或Reranker核心算法。
- 离线实验记录模型、参数、成本、延迟和每切片指标。
- 证据策略只能在分数完成校准后合并，生成器不得自行判断可信度。

### 8.3 验收

- `Recall@5 >= 0.80`。
- `MRR@10 >= 0.65`。
- Top 5重复条文率为0。
- hard-negative误报率达到批准阈值。
- P95检索延迟和单查询成本满足预算。
- 新策略可通过配置回退到阶段1 Retriever，不影响 API 契约。

## 9. 阶段2：异步索引 Worker

### 9.1 目标

将索引构建从 HTTP 进程移出，形成可恢复、可审计、幂等的异步作业。

### 9.2 工作包

- 合并 generation、manifest、文件锁和 active CAS 特性。
- 定义 Job 状态机、幂等键、租约、心跳、取消、重试和错误码。
- 初始使用 SQLite WAL 作为作业状态与待领取队列的单一事实源。
- Worker 通过窄端口调用 IndexBuilder，不依赖 FastAPI。
- 管理 API 返回 `202 + job_id`，复用统一管理鉴权、限流和审计。
- API 持续服务旧 active 索引，验证后再热加载新 revision。

### 9.3 验收

- 提交接口 P95小于200ms且不执行构建。
- 重复提交幂等，同一知识库只有一个活动构建。
- Worker/API重启后作业可恢复。
- 任意失败不改变 active；旧索引全程可查询。
- kill、超时、磁盘满、CAS冲突和租约过期测试通过。

## 10. 阶段3：PostgreSQL与pgvector

### 10.1 前置条件

- 阶段1.5检索质量已经达标。
- 阶段2作业和Artifact生命周期稳定。

### 10.2 工作包

- 定义 VectorStore Port 与 Repository契约测试。
- 建立 PostgreSQL migration、pgvector schema、索引策略和连接池预算。
- 通过离线回填、双写校验、shadow read和逐步切流迁移。
- PostgreSQL作业领取使用事务和 `SKIP LOCKED`，替换 SQLite Adapter。
- 文件Artifact保留为可回滚快照，不同时重写应用用例。

### 10.3 验收

- 数据量、向量维度、内容哈希和抽样结果一致。
- 新旧检索差异报告在批准范围内。
- 迁移可暂停、可重跑、可回滚。
- 数据库故障不会返回伪成功或污染旧索引。

## 11. 阶段4：评测平台与持续回归

阶段0的最小评测在本阶段升级为正式平台：

- 数据集版本、标注审核、切片和变更审批。
- PR小集合、nightly全集合和发布前线上模型评测。
- 指标趋势、置信区间、失败样本、延迟和成本统一报告。
- 模型、Prompt、数据、索引和代码版本可追溯。
- 指标下降自动阻断发布，不允许手工修改阈值绕过。

## 12. 阶段5：可观测性与SRE

- OpenTelemetry统一 trace、metric和结构化日志。
- 建立问答、检索、模型、Worker、数据库和索引SLO。
- 配置告警、容量预测、Runbook和故障演练。
- 每次请求关联 request ID、job ID、build ID和模型调用。

最小日志与指标从阶段0开始存在，本阶段负责平台化和SLO治理。

## 13. 阶段6：安全与AI治理

- OIDC/OAuth2、RBAC和最小权限管理面。
- Secret Manager、密钥轮换、依赖签名、SBOM和镜像扫描。
- 网络隔离、WAF、共享限流、不可篡改审计。
- Prompt注入、越权检索、敏感信息和模型输出治理。
- 数据许可、保留周期和删除流程可审计。

基础安全是每阶段门禁，本阶段负责完整治理体系。

## 14. 阶段7：规模化、韧性与发布治理

- 多副本无状态API、Worker水平扩展和容量模型。
- 缓存、连接池、背压、负载测试和成本预算。
- 蓝绿/金丝雀发布、自动回滚和版本兼容矩阵。
- 备份恢复、跨区域灾备、RPO/RTO和混沌演练。
- 发布证据包包含测试、评测、安全、性能和回滚结果。

## 15. 优先级总表

| 顺序 | 阶段 | 必须先解决的问题 |
|---:|---|---|
| 0 | 可复现基线 | 依赖、环境、数据来源、原始快照 |
| 1 | 模块化单体 | 分层、注入、top_k、SSE、错误契约 |
| 1.5 | 检索质量 | 数据完整性、召回、排序、分数校准 |
| 2 | 异步Worker | 作业持久化、幂等、原子切换 |
| 3 | PostgreSQL/pgvector | 可扩展存储和安全迁移 |
| 4 | 持续评测 | 版本化评测与发布阻断 |
| 5 | 可观测/SRE | SLO、告警、追踪和演练 |
| 6 | 安全治理 | IAM、供应链、网络和AI安全 |
| 7 | 规模与韧性 | 扩展、灾备和发布治理 |

任何阶段未满足退出门槛时，后续阶段只能做设计验证，不得进入生产合并。
